# NADIN V13

V13 includes the complete V12 interface and administration. Simple initial-password onboarding and optional personal passwords stay the same. Normal logins need no additional steps, CAPTCHA or new account setup.

## Progressive protection

V11 already limited login and recovery attempts. V13 replaces the fixed login limits with the Maarsen waiting-time sequence, adapted to NADIN's individual band accounts:

| Evaluated failed logins for an email address | Wait before another password can be checked |
| --- | --- |
| 1–5 | No lock |
| 6 | 30 seconds |
| 7 | 2 minutes |
| 8 | 10 minutes |
| 9 and later | 1 hour |

- The sequence is stored on the server and tied to the normalised email address. Switching IPs, cookies, browser or email capitalisation cannot bypass it. Unknown and expired addresses get the same failure/lock behaviour.
- A blocked request neither checks a password nor increases the counter or extends the lock. Waiting ends automatically. A successful login clears that account's failure streak; 24 hours without an evaluated failure also clears it.
- An additional rolling network limit locks a source IP for 10 minutes after 100 evaluated failures in 10 minutes, across all email addresses. Only `REMOTE_ADDR` is trusted, never arbitrary forwarded headers. Correct logins do not consume this budget or erase an attack's failures.
- Compared with Maarsen's single-PIN protection, the progression is per account and the 100-failure ceiling is per network, not installation-wide. This lets other members in the same rehearsal Wi-Fi continue after one person's typing errors, and avoids an attacker at another network locking the whole band.
- Existing sessions remain usable. Recovery keeps its independent V11 account/IP limits. A completed, valid password reset or authenticated password change clears the account's login streak; merely requesting a code does not. Network limits remain in force.
- Active limits already recorded by V11/V12 are honoured until their original expiry.

## Clear login feedback

Wrong credentials return a generic HTTP 401 response. Expired/invalid form tokens return 403 without consuming password attempts. Locks return HTTP 429 with `Retry-After` and a readable waiting time. With JavaScript, the waiting time counts down and the button becomes usable automatically; a different email can still be entered. The server enforces the wait independently of the countdown and JavaScript.

After a failed submission, the email stays in the form, safely escaped. The password is never echoed. No password is saved for later retries and no automatic login request is made. Password managers, paste and Show passwords continue to work. Error responses are not cached. Direct GET requests to the login handler simply open the login form.

## Storage and deployment

- Keep `config.inc.php` (especially the installation salt), `userdatei/userdatei.txt`, `userdatei/auth-v11.php`, `auth-v11-lock.php`, all music/gig data and hidden forScore identity files. Deploy all V13 source files together on top of V12; a clean V13 installation includes V12. No database or password migration is needed.
- The existing guarded, atomically replaced credential file stores the counters under the same file lock as password checking and session creation. Its filename and version remain compatible with V11/V12. Never delete it to clear a lock: that would remove personal passwords and trigger the missing-store safeguard.
- Attempt keys use HMAC with the installation's private storage key. The last 200 evaluated login events (success, failure, newly activated lock) are retained as `loginEvents` for operator diagnosis. They contain keyed account/network identifiers, timestamps and delay, not passwords, recovery codes, raw IPs or email addresses. Blocked retries do not flood this history.
- Expired counters are cleaned automatically. At 10,000 active counters, new identities are temporarily refused rather than evicting active protection or allowing unlimited storage growth. Recovery counters share this bound. Corrupt counter records fail closed.
- Keep the existing data-directory deny rules and HTTPS. If a reverse proxy supplies `REMOTE_ADDR` as its own address, configure client-IP handling at the trusted web-server boundary; V13 deliberately does not trust request-supplied forwarding headers.
- Application throttling limits password guessing; it does not replace hosting-level traffic protection. The remaining risk of an attacker temporarily locking a targeted account is bounded by the waiting time. Recovery and existing sessions remain usable.

The account-oriented design also follows [OWASP's authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) on account throttling and preserving a recovery path.

## Validation

All checks use isolated synthetic data; email is captured locally.

- `php tests/bruteforce.php`: 53 checks covering every stage, persisted locks, rotating IPs, normalised identities, shared networks, rolling windows, automatic expiry, password recovery/change, upgrade limits, concurrent PHP processes, bounded storage and diagnostics, and corrupt storage.
- `php tests/auth.php`: 67 existing authentication checks.
- `python3 tests/auth-http.py`: 56 HTTP account checks, including actual 401/403/429 responses, Retry-After, safe email retention, fresh cookies, forged forwarding headers and automatic unlock.
- `node tests/login-dom.cjs`: 8 software DOM checks for countdown, tab suspension, account changes, no automatic submission and password visibility.
- The V12 regression suite also runs: 104 administration HTTP checks, 29 administration DOM checks, and 40 forScore checks.

Runtime/dependency instructions and deployment details remain in [V12.md](V12.md). The generated views use actual PHP output and software DOM rendering with example data. The cloud browser cannot reach the local preview; production mail transport and native iPad/forScore imports still require their real environments.
