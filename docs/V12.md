# NADIN V12

V12 keeps the original grey/yellow interface, blue links, dense tune rows and contextual sidebar. It replaces the fixed-position gig editor and raw user-list editor with compact, responsive administration. V12 builds on V11, including personal passwords, simple initial-password onboarding and forScore.

## Everyday use

- Search current gigs in the sidebar and filter the library by tune title, ignoring case and accents.
- The selected gig has a visible heading and a direct Edit gig link for gig managers.
- Navigation and sheet-music links follow the person's permissions. Mobile password/logout links remain available even with a long email address.
- Password forms can show/hide all password fields without changing autocomplete or password-manager support.

## Gigs and setlists

- Manage gigs opens a normal page: gig list, editor and searchable library. Panels reflow at smaller widths instead of enforcing a 1400px workspace.
- Create a gig with a date and name. Names are normalised to Latin/ASCII filenames for compatibility with existing print/download tools; the resulting name is shown after saving.
- Add tunes with +, reorder by dragging or accessible up/down buttons, remove entries and undo the last 50 setlist edits. Repeated tunes are supported. Headings and breaks remain free text.
- Gig information and PDF attachments are in an expandable section. Save first, then upload/replace an attachment (PDF signature checked, maximum 20 MB or the lower hosting limit).
- Explicit Save, visible saved/unsaved state and a warning before discarding changes. Failed saves retain the editor's contents. Ctrl/Cmd+S uses form validation.
- Copy and rename retain attachments. Archive, restore and Deleted are explicit states. Deleted gigs and their PDFs can be restored. Collisions never overwrite an existing gig or attachment.
- Optimistic revision checks prevent another tab's edits from being overwritten. File locking serialises mutations, writes are replaced atomically, and protected safety copies are made before relevant overwrites.

## People and permissions

- Searchable people list, name/email fields, optional expiry and three groups of named permissions replace the editable CSV textarea.
- Templates: Band member, Substitute, Librarian, Band leader and Administrator. Templates are editable suggestions and do not save automatically. Instrument selections remain visible.
- Dependencies are explicit: PDF management needs info/audio management; managing tunes or gigs needs current-gig and library access. The UI selects required dependencies; the server rejects contradictory submissions.
- Unsplit Parts follow `vgigs`. `musers` also permits hidden media files, matching the existing access model; the label says so.
- Existing email addresses remain account identifiers. Add a new account when changing an address. This avoids silently transferring or resetting a personal password.
- Personal passwords survive rights/name edits. Affected old sessions are revoked. A permitted edit to the acting administrator's own account retains that browser's session.
- The acting administrator cannot delete or expire their own account or remove their own people-management right. At least one active people administrator must remain.
- Expiry keeps the original semantics: access ends at 00:00 on the selected date. The interface states this explicitly. No scheduled expiry uses 31.12.2099.
- Unknown extension permissions and unparseable legacy lines are preserved and reported, rather than silently removed. Unchanged people's original rows remain intact.

## Media and downloads

- Existing upload and media-management tools remain available. Mutations require POST and a session-bound CSRF token. Old direct GET mutation URLs no longer write data.
- Tune notes have revision checks; errors are surfaced in the containing editor even when the save response uses a hidden iframe.
- Tune renaming updates exact setlist entries in current, archived and deleted gigs, preserving info text, similarly named tunes, media filenames and the hidden forScore registry. Safety copies and rollback cover failed setlist updates.
- Only unused, empty tune folders can be removed; they are moved into `filesdeleted` for recovery. Deleting a media file no longer unlinks its source after a failed move.
- Viewing the library no longer silently renames folders/files. Internal identity files and old `zzDEL!` files are excluded from media lists.
- File downloads validate paths and exact setlist membership, section rights, library access and archive access. Similar tune-name prefixes do not confer access. Active document types download as attachments; `nosniff` and a restrictive content policy protect the download surface.
- ZIPs are built on demand from the current setlist and actual source hashes. A section ZIP includes unsplit Parts when that tune has no corresponding section PDF. Archive ZIPs and archived PDF attachments require archive permission. Protected hidden files and ambiguous multi-section filenames are excluded from ZIPs.
- The original iTunes/RSS service stays retired. Its obsolete gig-creation instruction is removed with the old composer.

## Installation and recovery

1. Back up the installation and deploy the V12 source files together, including all new `nadinmodule` files and the updated `get` handlers. Preserve the installation's `config.inc.php` settings, especially its salt, and all existing data.
2. Preserve `userdatei/userdatei.txt`, `auth-v11.php`, `auth-v11-lock.php`, media, hidden forScore identity files and all gig directories. V12 continues the V11 credential format; no database or password migration is needed.
3. The server needs write access to the existing data directories. New guarded `userdatei/admin-v12-lock.php`, `userdatei/zip-*.php` and `userdatei/revisions/*.php` are created as needed. Keep the existing deny rules for data directories and `abo`.
4. Keep `abo/zip`: it holds PDF attachments and generated ZIP caches. The `.sha256` cache companions can be rebuilt. Do not discard PDFs when clearing ZIP caches.
5. Include protected revisions and deleted folders in backups. Revisions contain a guarded JSON record with a base64 copy and original path; restore deliberately from backup when necessary. No automatic pruning of safety copies is performed.
6. Existing bookmarks to the old composer redirect to the new editor. Old raw `savegig.php`, `trx.php` and `saveusers.php` writes return HTTP 410. Integrations that wrote those endpoints must use the current UI/API with authentication and CSRF.
7. Verify the real hosting mail transport and a native iPad/forScore import before production use. Their services are unchanged; local tests capture mail and validate exported setlists without sending real mail or exercising the iPad app.

## Validation

The reproducible checks use isolated synthetic data and do not change production data:

- `php tests/auth.php`: 67 authentication checks.
- `php tests/forscore.php`: 40 forScore checks.
- `python3 tests/auth-http.py`: 40 account/integration checks, updated for the V12 people editor.
- `python3 tests/admin-http.py`: 104 V12 HTTP/storage checks, including actual create/save/copy/rename/archive/delete/restore, attachments, section ZIPs, stale edits, rights, media uploads/renames/deletes and path validation.
- `python3 tests/render-preview.py /tmp/nadin-preview`, then `node tests/admin-dom.cjs /tmp/nadin-preview/views`: 29 DOM behaviour checks with jsdom. No real browser or external request is used by the DOM checks.
- PHP syntax checks on all 140 PHP files and JavaScript syntax checks on the modified scripts.

Tests need Python `requests` and `beautifulsoup4`; DOM checks need jsdom 26.1.0. The application itself adds no JavaScript framework or database dependency. Set `NADIN_PHP` if PHP is not named `php`; set `NODE_PATH` when jsdom is installed outside the repository.

The cloud browser could not access the local preview server and rejected local-file navigation. Consequently the V12 preview is generated from the actual PHP output and DOM rendering; it is not a completed live-browser or native iPad acceptance test.
