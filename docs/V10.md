# NADIN V10 — personal passwords without losing simple onboarding

V10 builds on V9, including the original compact interface and forScore exports. There is no database or new account-registration process.

## What members and administrators do

- Add a member to the existing user list as before. Their existing email address and initial password work immediately. No compulsory password change interrupts onboarding.
- Members may choose **password** beside **logout** and set a personal password by supplying their current password. The initial password immediately stops working. Personal passwords are case-sensitive, allow spaces and paste, and require at least 12 characters (at most 72 UTF-8 bytes).
- The administrator's **access details** list shows initial passwords only for accounts that still use them. For other accounts it shows **Personal password set**, never the old initial password or the new password.
- **First login or forgotten password?** emails the existing initial password to an active member who has not changed it. Otherwise it emails a random single-use recovery code, valid for 30 minutes. Enter it via **I have a recovery code** and set a new password. No password or session is changed merely by requesting a code. Up to three outstanding codes can coexist; successful use invalidates all of them.
- Changing a password revokes every old session while keeping the changing browser signed in with a fresh session. Recovery revokes every session and returns to the normal login form. Logout revokes that browser's token on the server.
- A removed or expired member cannot log in or recover access. Permission changes invalidate existing sessions and recovery codes. Ordinary user-list editing preserves personal passwords. Removing an account deletes its stored credentials; registering that email again starts a new initial-password account.

## Implementation and limits

Personal passwords use PHP's `password_hash`/`password_verify` (Argon2id when available, bcrypt otherwise). Random 256-bit session tokens are stored only as hashes, have server-side inactivity expiry, and use a separate HttpOnly, SameSite=Lax cookie scoped to the installation directory. HTTPS produces Secure cookies; configure HTTPS correctly on the host/proxy. The old reusable `u`/`p` cookies are not accepted. Optional IP binding remains supported.

Password changes require the current password and a session-bound CSRF token. Login, recovery and reset forms have browser-bound CSRF tokens. User editing has a session-bound CSRF token. Account and IP limits bound login, recovery and reset attempts. Recovery responses do not disclose whether an email is registered; unknown/expired addresses receive no mail. No password, recovery code or session token is written to the login log. Password change/reset sends a notification without the password.

The recovery code avoids putting credentials into a URL, browser history or referrer, and requires no extra public-URL setting. The mail tells members to open their band's NADIN as usual. The mail request does not silently choose a new password or re-enable the initial one.

`userdatei/auth-v11.php` holds credential hashes, session hashes, reset-code hashes and request-limit state. `userdatei/auth-v11-lock.php` serialises writes and records successful initialisation. Writes use atomic replacement. Both have executable PHP guards and restrictive file modes; retain the existing web denial on `userdatei`. Corrupt storage or disappearance of the credential file after initialisation fails closed, instead of reviving initial passwords. Preserve **both files** with `userdatei.txt` in backups. Restore them together. A backup rollback also rolls back credentials, so treat authentication-state restoration as an administrative recovery action.

Limits: 12 login attempts per account / 15 minutes; 60 per source IP / 15 minutes. Three access emails per account / hour, 20 per source IP / hour. Five reset attempts per account / 15 minutes and 30 per source IP / 15 minutes. Limits release automatically. No CAPTCHA or external identity service is introduced. Access expiry retains the original midnight boundary of the date in the user list.

## RSS/iTunes retirement

The old RSS/iTunes feature has been retired rather than extended: it depended on separately regenerated `.htpasswd` files, HTTP Basic Auth and old feed-rewrite routes. It would otherwise preserve an independent credential path that could outlive a personal-password change.

- Subscription controls are disabled even if an old config still sets `offeritunesabo=yes`.
- Feed, Basic Auth and old feed-download PHP endpoints return HTTP 410. Apache direct access under `abo/` is denied; it can therefore return 403 before PHP runs. Legacy rewrite rules are replaced with denials.
- The access-details screen no longer writes `.htpasswd` files. Old files under `userdatei` can remain protected and unused.
- **Do not delete `abo/zip`.** Gig PDF attachments, section ZIPs and audio ZIPs still use it through the authenticated `get/` handlers. Individual recordings, in-browser listening, the media library, all current/archive Rep features and V9 forScore remain available.
- Preview/ZIP generation now requires the existing `mgigs` manager right.

## Deploying an existing installation

Use PHP 7.4 or later (validation used PHP 8.3). Deploy the changed/new source files and the changed `.htaccess` files, retaining the installation's own config values, especially `$salt`, the user list, music/media, Reps and `abo/zip`. Do not replace production `config.inc.php` wholesale. The removed RSS settings can remain in a local config; they are ignored. The server must be able to write `userdatei`, as before. Existing sessions require one fresh login after upgrade, using their existing passwords.

If password mail already uses a hosting-specific SMTP implementation, preserve it as `userdatei/mail-adapter.php` defining `nadin_mail_transport($to, $subject, $message)` and returning a boolean. The bundled fallback uses PHP `mail()` and the existing `$mymail` / `$useheadersinphpmailcommand` configuration. No SMTP credentials are included. Test real delivery on the target host before rollout; local tests capture mail and cannot verify an external inbox. Failed mail submission is logged server-side; the public response remains generic.

Deploy all changed `abo/.htaccess`, `abo/rss/.htaccess` and `abo/rwtest/mitrw/.htaccess` files so legacy Basic Auth/rewrite paths are retired on existing installations too. On non-Apache hosts retain equivalent denials for data directories and `abo`. Keep `tests/` out of production (or deny it at the web-server level); the PHP test entry points additionally reject web execution.

## Validation

- 67 authentication checks: initial/personal login, exact account/rights/expiry checks, case and Unicode handling, CSRF, session revocation, reset expiry/reuse, request limits/release, removal and permission changes, corrupt/missing storage, concurrent logins and simultaneous use of one recovery code.
- 40 HTTP/integration checks against an isolated PHP server under `/band/nadin/`: real forms/cookies/redirects, mail captured locally, password changes and reset, admin UI, user saving, forScore, retired endpoints, gig attachments, ZIP permissions and server-side logout.
- 40 existing forScore regression checks remain green.
- PHP syntax checks across all 133 PHP files; JavaScript syntax checks for the retained layout scripts; whitespace/diff checks.

Native iPad forScore import and delivery through the production mail service remain deployment/acceptance checks. No production users or media were used in testing.
